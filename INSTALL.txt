=====================================================================
 MonsterList — upload & install guide (cPanel / shared hosting)
 Requirements: PHP 8.0+ (with pdo_mysql, gd, curl, fileinfo), MySQL 5.7+/MariaDB 10.3+
=====================================================================

STEP 1 — UPLOAD THE FILES
-------------------------
Upload EVERYTHING in this package straight into public_html.
The package root is the web root: index.php, .htaccess, assets/, uploads/
plus app/, database/ and scripts/ (those three are protected from web
access by their own .htaccess files).

Make sure the uploads/ folder is writable (755 usually; 775 if required).

AUTOMATIC UPDATES (optional, recommended): see DEPLOYMENT section at the
bottom — pushes to the GitHub repo can auto-update your site.

STEP 2 — CREATE THE DATABASE
----------------------------
cPanel → MySQL Databases:
  1. Create a database (e.g. youruser_monsterlist)
  2. Create a database user with a strong password
  3. Add the user to the database with ALL PRIVILEGES

STEP 3 — IMPORT THE SQL FILES (phpMyAdmin → Import), IN THIS ORDER
------------------------------------------------------------------
  1. database/schema.sql             (tables — required)
  2. database/upgrade-all.sql        (everything added since schema.sql was
                                      written — required, see below)
  3. database/seed.sql               (countries, states, cities, categories — required)
  4. database/create-superadmin.sql  (your admin login — required;
                                      edit the email in the file first!)
  5. database/demo-data.sql          (OPTIONAL: 695 demo listings so pages
                                      aren't empty; fresh installs only)

  ABOUT upgrade-all.sql
  Releases that add a table or column ship a numbered upgrade-v*.sql. Each
  has to be run once, in order, and a plain ALTER fails outright if the
  column is already there — which stops the rest of the batch. Half-applied
  databases are easy to end up with and unpleasant to get out of.

  upgrade-all.sql replaces the whole set. Every step checks first and skips
  what is already done, so it is safe on a database that is fully current,
  partly upgraded, or years behind, and safe to run again any time. It only
  ever adds — it drops no table, no column and no row.

  Run it after ANY release that says the database changed. It prints a
  report at the end; every line should read OK. Superadmin → Diagnostics
  says the same from inside the site.

  (The numbered files are still in database/ for reference. You do not need
  them if you run this one.)

STEP 4 — CONFIGURE
------------------
  1. Copy  app/config.example.php  →  app/config.php
  2. Edit app/config.php:
       site_url  → https://monsterlist.org   (no trailing slash)
       db        → host (usually 'localhost'), database name, user, password
       mail.from → no-reply@monsterlist.org (create this mailbox in cPanel
                   so mail passes SPF checks)

STEP 5 — FIRST LOGIN
--------------------
  1. Visit https://monsterlist.org/superadmin/login  (staff sign-in;
     members use /login)
  2. Log in with the email from create-superadmin.sql
     and password:  ChangeMe-2026!
  3. IMMEDIATELY change the password (top-right → My account → Settings)
  4. Check Superadmin panel → Settings: site name, tagline, plan pricing

STEP 6 — STRIPE (monthly memberships)
-------------------------------------
Do the whole of this with the Test/Live toggle in Stripe set to TEST
first. Keys and price IDs are per-mode: a live price ID under a test key
looks perfectly valid and fails only when a member tries to pay.

  1. dashboard.stripe.com → Product catalogue → add two products, each
     with ONE recurring MONTHLY price:
        Pro       $19.00 / month
        Featured  $49.00 / month
     (These must match the figures in Superadmin → Settings, which are
     what the pricing page prints. Stripe is what actually charges.)

  2. Open each product and copy its PRICE id — the one starting
        price_...
     NOT the product id starting prod_.... This is the single most
     common mistake and Diagnostics checks for it.

  3. Superadmin panel → Settings → paste them into
        Pro price ID
        Featured price ID

  4. Stripe → Developers → API keys → copy the secret key (sk_test_...)
     into app/config.php:
        'stripe' => [
            'secret_key'      => 'sk_test_...',
            'publishable_key' => 'pk_test_...',
            'webhook_secret'  => '',        // filled in at step 5
        ],

  5. Stripe → Developers → Webhooks → Add endpoint:
        https://monsterlist.org/stripe/webhook
     Events:  checkout.session.completed
              customer.subscription.updated
              customer.subscription.deleted
     Copy its signing secret (whsec_...) into app/config.php.

     Upgrades work without this — the site confirms the payment itself
     when the member returns from Stripe. The webhook is what tells the
     site about everything that happens LATER: a card that fails, a
     cancellation, a renewal. Without it a member who cancels in Stripe
     keeps their plan here forever.

  6. Superadmin panel → Diagnostics → "Stripe payments". Every row must
     be a tick. It looks the two price IDs up in Stripe, so it catches a
     wrong ID, an archived price, a one-off price where a subscription
     was meant, and a test/live mismatch.

  7. Sign up as a test member, press Upgrade, pay with Stripe's test card
        4242 4242 4242 4242, any future expiry, any CVC
     You should land back on your listing with the new plan already
     applied. Check Superadmin → Members shows the new plan.

  8. Only then: flip Stripe to LIVE, repeat steps 1-5 with the live
     product, live price IDs and live keys (they are all different), and
     re-check Diagnostics.

STEP 6b — AI FILL (optional but recommended)
--------------------------------------------
Members can paste their website URL on the New Listing form and AI
pre-fills everything. To enable:
  1. Get an Anthropic API key at https://platform.claude.com (API keys)
  2. Log in as superadmin → Superadmin panel → Settings → "AI fill (Anthropic API)"
     → paste the key → Save. (No file editing needed.)
Cost guide: each fill is one Claude API call (typically a few cents).
Members are limited to 10 fills per hour. Leave the key empty to
disable the feature — the form works normally without it.

The same key also powers "Write it with AI" under the Profile box in
Superadmin -> Listings -> edit, which researches a business and writes
its 1,000-1,500 word Profile section. That one uses Claude's web search
and web fetch tools, so it costs more than a fill (roughly the price of
a short article) and takes a minute or two. If it reports that it could
not search, web search is switched off for the key: turn it on at
https://platform.claude.com -> Settings.

STEP 7 — GO-LIVE CHECKLIST
--------------------------
  [ ] https:// works (the .htaccess already forces HTTPS)
  [ ] /robots.txt loads and shows your sitemap line
  [ ] /sitemap.xml loads (then submit it in Google Search Console
      and Bing Webmaster Tools)
  [ ] /llms.txt loads
  [ ] Sign up a test member, create a listing, approve it in /superadmin
  [ ] The approval email arrived (check spam; if unreliable, ask about
      SMTP — see README)
  [ ] Demo data decision: keep it, or clean it out with this SQL:
        DELETE FROM businesses WHERE owner_id IS NULL AND email LIKE '%@demo.invalid';
        UPDATE cities SET listing_count = (SELECT COUNT(*) FROM businesses
          WHERE city_id = cities.id AND status = 'live');

TROUBLESHOOTING — HTTP 500 FIRST AID
------------------------------------
  1. Open  https://yourdomain/install-check.php  in your browser.
     It tests everything (PHP version, extensions, config, database,
     folders) and tells you exactly what to fix, in order.
     → DELETE install-check.php once the site works.

  2. The three most common causes, in order:
     a) PHP VERSION — the app needs PHP 7.4+, 8.1+ recommended.
        cPanel → MultiPHP Manager (or "Select PHP Version") → set 8.1/8.2/8.3
        for the domain.
     b) app/config.php missing — Step 4 not done yet.
     c) Wrong DB credentials in app/config.php — or the DB user was created
        but never ADDED to the database (cPanel → MySQL Databases → bottom
        section "Add User To Database" → All Privileges).

  3. Still stuck? Set 'debug' => true in app/config.php, reload the page,
     and read the real error message. Set it back to false afterwards.

OTHER ISSUES
------------
  • Pretty URLs 404               → .htaccess didn't upload (it's a hidden
                                    file — enable "show hidden files" in
                                    your file manager)
  • Blank white page              → same as 500: run /install-check.php
  • Images won't upload           → uploads/ folder missing or not writable

=====================================================================
 DEPLOYMENT — automatic updates from GitHub
=====================================================================

OPTION A — GitHub Actions FTP deploy (works on every Hostinger plan)
--------------------------------------------------------------------
The repo ships .github/workflows/deploy.yml. One-time setup:
  1. Hostinger hPanel → Files → FTP Accounts: note the FTP host,
     username, and password (create an account if needed).
  2. GitHub repo → Settings → Secrets and variables → Actions →
     add three secrets: FTP_SERVER, FTP_USERNAME, FTP_PASSWORD.
  3. Done. Every push to the repo now uploads the changed files to
     public_html automatically (your app/config.php and uploads/ are
     never touched). You can also trigger it manually from the
     GitHub Actions tab ("Run workflow").

OPTION B — Hostinger's built-in Git deployment
----------------------------------------------
hPanel → Advanced → GIT:
  1. "Create a New Repository": paste the repo's clone URL and branch.
     For a private repo, hPanel shows an SSH key — add it on GitHub
     under repo → Settings → Deploy keys.
  2. Directory: public_html. NOTE: Hostinger requires the target
     directory to be EMPTY on the first deploy. If your site is
     already there: temporarily move app/config.php and uploads/
     aside (File Manager), empty public_html, deploy, then move
     config.php and uploads/ back.
  3. Enable "Auto Deployment" — hPanel gives you a webhook URL; add
     it on GitHub under repo → Settings → Webhooks. Every push then
     updates the site.

With either option, database changes are NOT automatic — when an
update ships a file like database/upgrade-vN.sql, import it once via
phpMyAdmin after the deploy.
